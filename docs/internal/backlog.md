## 1. Динамические поля не знают, для какого контроллера их спрашивают

Заведено 20.08.2026, найдено замером спеки printable.

`@input [methodName]` — механизм, которым контроллер отдаёт набор полей в
рантайме, вместо того чтобы перечислять их тегами. Вызывается он так:

```php
$callable = "{$class}@{$matches['callable']}";
$descriptions = app()->call($callable);
```

То есть метод спрашивают «какие у тебя поля», не сказав, **для какого
действия и под каким ключом контроллера** сейчас строится спека. Пока
класс контроллера обслуживает один маршрут, разницы нет. Как только один
класс обслуживает много — механизм становится бесполезен ровно там, где он
нужнее всего.

**Живой пример.** В laravel-admin один `ResourceController` обслуживает все
ресурсы панели: `admin/clients/create`, `admin/plans/create`,
`admin/credentials/create` — один класс, разные наборы полей. Метод не
может ответить «поля для `clients`», потому что его про `clients` не
спросили. В результате 41 операция панели printable объявляет тело без
единого поля, хотя каждая валидирует `$resource->validationRules()`.

**Правка.** Передавать в callable контекст — версию, ключ контроллера,
действие:

```php
$descriptions = app()->call($callable, [
    'apiVersion' => $version,
    'controllerKey' => $controller,
    'action' => $action,
]);
```

`app()->call()` подставляет только те именованные параметры, которые метод
объявил, так что существующие реализации без аргументов продолжают
работать. Изменение обратно совместимо — минорная версия, не мажорная.

Размер работы, чтобы не показался больше, чем есть: контекст нужно
протащить в `getParametersByTags()` — она вызывается из
`getOpenApiPaths()`, где `$version`, `$controller` и `$action` уже в
области видимости, то есть это один лишний параметр у одного приватного
метода. Публичная поверхность не меняется вовсе.

Записи по ту сторону: `laravel-admin/docs/internal/roadmap.md` (провайдер
поверх `Resource::fields()`), `printable/docs/internal/plan/backlog.md`
BL-45.

## 2. `api:lint` не видит отсутствия разметки

Заведено 20.08.2026, оттуда же.

Линтер сверяет разметку с литеральным `$request->validate([...])`. Где
правил нет или они собираются в рантайме — сверять не с чем, и молчание
трактуется как «всё в порядке». Поэтому пункт 1 дожил до ручного замера:
ни одна из 28 проверок его не показала.

Правило «действие не объявляет входа вовсе» в лоб не годится: из 216
таких операций printable 175 вход и правда не принимают
(`system/bootstrap`, `system/me`, `notifications/unread`), то есть три
четверти срабатываний были бы ложными — а линтер, который кричит зря,
перестают читать. Это ровно та ошибка, от которой в самом пакете уже есть
защита: `@security` не проверяется, пока приложение не объявило ни одной
схемы.

Сузить можно по-разному, и выбор стоит сделать по замеру, а не по
ощущению:

- требовать разметку только там, где контроллер **что-то** валидирует —
  пусть и не литералом (тело метода содержит `validate`, `Validator::make`,
  FormRequest);
- отдельным правилом ловить `@input [method]`, который вернул пустой набор:
  объявление динамических полей, не давшее ни одного поля, — это отказ
  механизма, а не «полей нет»;
- считать подозрительными глаголы действий (`create`, `update`, `search`),
  оставив остальным презумпцию невиновности.

Первое честнее прочих: оно опирается на код, а не на имя.

## 3. `@default` и `@example` не заполняет никто

Заведено 20.08.2026. Не дефект — наблюдение, важное для планирования.

Замер по 685 операциям реального приложения: **ноль** несут хотя бы один
`@default` или `@example`. Теги существуют, документированы, работают и не
использованы ни разу.

Это стоит помнить всякий раз, когда возникает мысль добавить в пакет
разметку для данных — пресеты, фикстуры, кейсы автотестов. Эксперимент
«дать теги и ждать, что их заполнят» уже поставлен, и результат известен.
Данные в докблок не переезжают; если они когда-нибудь понадобятся, брать
их придётся из кода или из записанного трафика.
